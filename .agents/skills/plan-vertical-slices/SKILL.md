# 按完整功能链路拆分任务

以技术负责人视角规划渐进式交付。默认进行需求核对和任务拆分。新功能按下文的阶段约定进入开发。

## 规划模式

1. **确认项目现状。** 阅读适用的 `AGENTS.md`、`docs/PRD.md`、`docs/ARCHITECTURE.md`、现有任务记录及相关代码和测试。若项目采用其他路径，使用对应的现有资料。核对入口、数据与测试覆盖，找出已实现能力、缺口和可复用依赖。资料缺失或相互矛盾时，先完成有依据的拆分，注明待确认事项。资料缺口确实阻止任务推进时，标记「受阻」并说明原因。需求 ID、架构决策和完成状态须有来源或可核实依据。
2. **梳理业务链路。** 从用户入口、主要操作、业务处理到用户可见结果或反馈，记录影响验收的异常路径和依赖。范围以当前 PRD 已确认的近期需求及必要前置能力为限。存在明确的本轮目标时，围绕该目标规划。
3. **切分并排序。** 每个任务交付一个可运行、可独立验收的业务结果，控制在一次相对独立的实现、测试和审查周期内。按需跨 UI、服务和数据层，沿用现有架构及可复用能力。大功能可先交付一条完整可用的主路径，再逐步补齐其他可验收场景。必要前置能力可独立成卡，写明它解锁的业务任务及可验证结果。空目录、空类和空接口不作为交付成果。先满足依赖，再按用户价值和实施风险排序。避免擅自引入重大技术方案、扩大产品范围或提前拆解未确认需求。
4. **校验拆分。** 逐卡确认规模适中、边界清楚、有可执行的验收条件、依赖真实且完整。合并没有独立交付价值的零碎步骤，拆开相互独立的功能，去掉现有实现已经覆盖的内容，并确认每一步都能形成可运行或可验证的成果。
5. **输出并维护。** 初次输出核心业务链路、按依赖顺序排列的任务列表、任务卡，以及建议优先执行的任务和原因。优先复用项目已有任务管理机制。没有现成机制且需要落盘时，可使用 `docs/TASKS.md`。增量规划只调整受影响的任务。发布后的历史记录以原 ID 保持可追溯。规划阶段产出任务和验收约定。

### 调整既有顺序

把新任务排到实际执行的位置。先判断用户指定的顺序、任务依赖和返工成本。若改动会建立后续功能共用的页面、接口或数据基础，明确哪些后续任务必须等它验收，以及哪些准备工作仍可并行。可分批验收的工作可用一个父任务和内部阶段表示，主任务顺序应能直接看出下一步。

默认保留稳定 ID，用执行顺序和依赖表达插入关系。项目以顺序编号表达执行计划，且用户明确要求插入指定编号时，按范围顺延可调整的未开始任务，保留已完成记录、需求 ID 和已建立的外部引用。涉及历史记录或外部引用时，使用可追溯的编号映射或独立排序字段。同步核对任务卡、依赖、需求文档、原型、验收记录与交接中的引用。

### 任务卡

**任务 ID｜任务名称**（状态）

- **关联需求** — 填写真实 PRD 需求 ID。源文档无 ID 时引用章节或原需求标题。
- **目标** — 描述本轮交付后用户或业务可获得的结果。
- **实现范围** — 列出完成该结果所需的核心行为。
- **非目标** — 列出容易与本任务混淆的范围边界。
- **前置依赖** — 写明依赖的任务 ID 或必须具备的现有能力。没有依赖时注明。
- **验收标准** — 给出可执行的操作或条件及可观察的预期结果，覆盖主路径和影响交付的异常路径。

仅在确有影响时补充关键技术风险。无需预列每个函数、文件或实现步骤。任务状态使用「待开发」「开发中」「待验收」「已完成」「受阻」。

## 开发执行模式

1. **开工说明。** 核对指定任务的 PRD、架构约束、前置依赖及真实代码。第一次修改产品代码前，在对话中单独发出能据此核对实施范围的说明。
   - 从真实入口按执行顺序写清谁能操作、输入、关键判断、实际读写和用户可见结果。用 Mermaid 或文字箭头标出会改变结果的失败分支，写明具体触发条件、提示、数据是否写入，以及用户如何重试或恢复。
   - 点明相关接口的输入输出、表和关键字段，并说明方案解决的具体问题。给出真实验收入口、验证条件和主路径及关键失败分支的预期结果。
   - 从已确认原型转入完整实施时，即使用户最后只改了局部文案，也按完整功能范围说明。纯文案或样式改动交代位置、可见影响和验证方式即可。所需确认已取得时，发出说明后按适用的 `AGENTS.md` 和已确认方案继续执行。
   - 注释和文档字符串统一使用简体中文。每个函数和方法都写注释或文档字符串，直观说明对具体对象做什么、产生什么结果；关键参数和变量写清含义、用途及对结果的影响。需要时说明业务约束、设计原因和失败后果。避免“处理数据”“执行逻辑”等抽象表述和逐行复述代码；协议标记、标识符和工具规定的英文保持原样。新增或修改代码时同步补齐相关注释，已有代码的补充按当前任务范围进行。
2. 运行必要测试并通过功能的正常入口进行实际验证。涉及 UI 时，实际打开界面检查视觉呈现并操作关键流程。对照任务卡、PRD 和架构约束逐项核验。
   - 本机开发和验收时，通过 Docker 或 Docker Compose 启停应用服务及其数据库、缓存等中间件，优先复用合适的本地镜像，避免重复拉取。本机使用容器数据库时，配置端口映射以便本机数据库工具连接，默认仅绑定 127.0.0.1；先检查端口占用，发生冲突时选择可用主机端口，并在运行文档说明连接地址、端口和数据卷保留方式。服务器部署按目标环境确认的配置和镜像策略执行。本机专用配置通过显式启用的覆盖文件或本机环境变量提供。
3. 更新既有任务记录和必要文档。涉及 README 时按企业级项目文档编写，语言简洁、面向使用部署和维护，避免演示口吻及冗余解释；根据真实实现和验证记录内容，开发中也采用成熟项目的组织方式，未实现或未验证的内容如实标明。只有必要验收通过后才标记「已完成」。尚待验收时使用「待验收」，存在实际阻塞时使用「受阻」并写明原因。
4. **最终交付。** 在最终答复正文写清实际改了哪些逻辑，使用户无需回看过程消息。沿真实入口交代本轮改变的关键判断、涉及的接口与数据读写、成功和关键失败分支的可见结果与恢复方式。有影响的实施偏差写明实际做法与原因。按改动规模取舍，简单改动交代具体位置、行为和验证即可。
   - 给出实际验证结果、未验证项和剩余风险。测试、构建和界面检查的范围及结果写入验收记录或交付汇报。部署、建库、迁移、备份和恢复的操作步骤写入项目运行或维护文档。
   - 发送前对照项目 `AGENTS.md`、开工说明和实际改动回读最终答复。若正文只有功能清单、文件列表、测试结果或文档链接，先补齐本轮实际逻辑再交付。

### Git 提交文案

- 获授权为功能交付提交时，先核对用户要求和项目 AGENTS.md。默认标题为 `类型(范围): 中文摘要`，范围可省略。简单改动用一行。复杂改动在标题后空一行，用 `- 【新增】 …`、`- 【修改】 …`、`- 【修复】 …` 说明实际变更和影响。
- 提交前逐条对照 diff。每条正文交代一个功能或模块的具体对象和变化。数据结构变化放到所属功能，说明表、字段或约束及其用途。原型本身是交付内容时，标题注明设计或原型，正文说明交互。测试代码本身是交付内容时，写清新增的覆盖行为。验证次数、测试和构建结果、浏览器验收写入验收记录或交付汇报，环境操作步骤写入运行或维护文档。需求确认与文档同步过程留在项目文档。

## 从规划转入单个功能

完整项目规划先列出功能顺序和依赖。功能细节待确认时将卡片标为待细化，聚焦用户本轮选定的功能。

1. **确认需求。** 用户说「开始下一块功能」「做下一个任务」等时，核对任务卡和现有实现，用 maintain-prd 与用户确认本功能尚未明确的业务规则及验收条件。已有确认可以沿用。涉及界面的功能在业务规则和验收条件确认后进入原型设计。
2. **确认原型。** 用 design-product-ui 交付可查看的高保真原型。关键交互应可操作，附预览入口和需要评审的状态。等待用户明确确认当前原型。已有经用户确认、覆盖本轮范围的原型时可引用它。
3. **进入开发。** 需求和适用原型都获得确认后，先完成「开发执行模式」的开工说明，再在用户已授权的范围内修改产品代码。任一阶段仍待确认时，交付当前阶段可评审的成果并说明待确认项，暂停对应功能的产品代码、接口和数据库迁移。无需界面设计的任务在需求确认后也先完成开工说明。

小修复和纯重构按影响范围简化。用户明确要求调整阶段顺序时，按当前指示执行。
