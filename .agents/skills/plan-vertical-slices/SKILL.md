# 按完整功能链路拆分任务

以技术负责人视角规划渐进式交付。默认进行需求核对和任务拆分。用户明确要求实现某个任务后，才进入该任务的开发执行模式。

## 规划模式

1. **确认项目现状。** 阅读适用的 `AGENTS.md`、`docs/PRD.md`、`docs/ARCHITECTURE.md`、现有任务记录及相关代码和测试。若项目采用其他路径，使用对应的现有资料。核对入口、数据与测试覆盖，找出已实现能力、缺口和可复用依赖。资料缺失或相互矛盾时，先完成有依据的拆分，注明待确认事项。资料缺口确实阻止任务推进时，标记「受阻」并说明原因。需求 ID、架构决策和完成状态须有来源或可核实依据。
2. **梳理业务链路。** 从用户入口、主要操作、业务处理到用户可见结果或反馈，记录影响验收的异常路径和依赖。范围以当前 PRD 已确认的近期需求及必要前置能力为限。存在明确的本轮目标时，围绕该目标规划。
3. **切分并排序。** 每个任务交付一个可运行、可独立验收的业务结果，控制在一次相对独立的实现、测试和审查周期内。按需跨 UI、服务和数据层，沿用现有架构及可复用能力。大功能可先交付一条完整可用的主路径，再逐步补齐其他可验收场景。必要前置能力可独立成卡，写明它解锁的业务任务及可验证结果。空目录、空类和空接口不作为交付成果。先满足依赖，再按用户价值和实施风险排序。避免擅自引入重大技术方案、扩大产品范围或提前拆解未确认需求。
4. **校验拆分。** 逐卡确认规模适中、边界清楚、有可执行的验收条件、依赖真实且完整。合并没有独立交付价值的零碎步骤，拆开相互独立的功能，去掉现有实现已经覆盖的内容，并确认每一步都能形成可运行或可验证的成果。
5. **输出并维护。** 初次输出核心业务链路、按依赖顺序排列的任务列表、任务卡，以及建议优先执行的任务和原因。优先复用项目已有任务管理机制。没有现成机制且需要落盘时，可使用 `docs/TASKS.md`。增量规划只调整受影响的任务，保留既有任务 ID 和状态。规划阶段不修改产品代码。

### 任务卡

**任务 ID｜任务名称**（状态）

- **关联需求** — 填写真实 PRD 需求 ID。源文档无 ID 时引用章节或原需求标题。
- **目标** — 描述本轮交付后用户或业务可获得的结果。
- **实现范围** — 列出完成该结果所需的核心行为。
- **非目标** — 列出容易与本任务混淆的范围边界。
- **前置依赖** — 写明依赖的任务 ID 或必须具备的现有能力。没有依赖时注明。
- **验收标准** — 给出可执行的操作或条件及可观察的预期结果，覆盖主路径和影响交付的异常路径。

仅在确有影响时补充关键技术风险。无需预列每个函数、文件或实现步骤。任务状态使用「待开发」「开发中」「待验收」「已完成」「受阻」。

## 开发执行模式

1. 重新核对指定任务的 PRD、架构约束、前置依赖及真实代码，拟定简洁的实现计划，按适用的 `AGENTS.md` 开发。
2. 运行必要测试并通过功能的正常入口进行实际验证。涉及 UI 时，实际打开界面检查视觉呈现并操作关键流程。对照任务卡、PRD 和架构约束逐项核验。
3. 更新既有任务记录和必要文档。只有必要验收通过后才标记「已完成」。尚待验收时使用「待验收」，存在实际阻塞时使用「受阻」并写明原因。
4. 简要报告交付内容、实际执行的验证及结果、未验证项和剩余风险。以可观察的验收结果为准，如实记录验证范围和结果。
