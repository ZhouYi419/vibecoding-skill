# 设计与维护软件架构

以技术负责人的视角，为已确认的需求设计可维护、可测试的最小合理架构。优先沿用有效的现有技术和模块，为后续变化保留清晰的职责与依赖边界。只有当前需求、实际风险或维护收益足以证明必要性时，才引入新的基础设施、抽象或依赖。

## 确定依据与模式

- 定位目标项目，阅读适用的 `AGENTS.md`、最新 PRD 和已有架构文档。检查相关代码、依赖声明、运行配置和测试，区分已验证现状、已确认约束、建议和待验证假设。沿用现有文档路径，新项目默认使用 `docs/ARCHITECTURE.md`。
- 围绕已确认功能、运行平台、部署约束、维护成本及实际安全和可靠性风险设计。普通缺口可用明确标注的工作假设推进。只有重大选型、系统边界或架构安全确实依赖用户决策时才提问，每轮原则上最多两个，并给出推荐与理由。涉及版本、兼容性或支持周期时，以实际项目声明和官方资料为依据，未验证的结论标明状态。
- 根据请求选择初次设计、增量设计或架构审查。架构设计阶段交付文档或建议，具体代码实现按用户请求另行开展。

## 初次架构设计

1. 从 PRD 提炼近期功能、核心链路和技术约束。对重要选型给出一项明确推荐、理由及有意义的主要替代方案与取舍。
2. 设计模块职责、依赖方向和接口边界，说明主要数据流、关键数据实体、状态归属和持久化方式。将核心业务规则放在便于独立测试的位置。按实际需要写明目录职责、安全边界、异常恢复和验证策略。
3. 复核架构能否覆盖当前核心需求，模块是否可独立测试，是否存在循环依赖、重复能力、过度抽象或重要的安全和数据一致性缺口。对会影响选型的未验证假设给出具体的最小验证方法。
4. 保存完整但精炼的 `ARCHITECTURE.md`。文档应覆盖技术目标、选型、系统组成、模块和依赖、数据和状态、目录职责、关键约束与测试、主要风险及首个开发切入点。简单系统用简短的流程或表格表达，复杂关系可加图。

## 增量设计与架构审查

- **增量设计** — 依据本轮已确认需求和现有实现，定位受影响的模块、接口、数据和依赖。先判断能否局部扩展，给出最小方案、风险和必要验证。只有模块职责、关键依赖、数据归属或重要架构决策确有变化时，才更新总体架构文档的相关部分。
- **架构审查** — 以真实代码和测试为依据，定位可复现的问题或可核实的文档偏差，说明影响、最小修正方案和回归验证方式。涉及重大架构变更时先说明取舍，待确认后在授权范围内同步文档和实现。发现 PRD 与代码不一致时，先识别实现偏差或已确认的需求变更。

## 交付与任务规划衔接

- 保存后回读文档，确认路径、需求依据、模块依赖和关键约束一致。首次交付完整架构；增量工作简述本轮影响、修改和风险。无法写入时提供可保存的 Markdown，并如实说明保存状态。
- 从已确认的 PRD 功能 ID 或章节中推荐一个能验证架构的最小完整业务链路，说明入口、关键模块和数据流、用户可见结果、必要前置条件和验收重点。交接给 `$plan-vertical-slices` 时提供 PRD 与架构路径及仍会影响拆分的待决项。按需进入任务规划。
