# 产品 UI 设计与验收

围绕用户要完成的操作组织页面。用构图、视觉层级、留白、字体和颜色突出主要任务，兼顾清晰反馈和可用性。复用已有设计变量、组件和布局。把“视觉稿”“暂定名称”等评审标记，以及原型限制、设计说明和假设放在交接说明中。装饰与动效以有实际用途为准。

## 界面文案

- 每段文案都应帮助用户识别页面或控件、作出决定、完成操作或理解状态。删掉复述相邻标题、按钮、表头或列表内容的副标题和说明，以及仅起装饰作用的标语、徽章和编号。保留必要的表单标签、无障碍名称、约束、操作后果和反馈。
- 检查时把文案与同屏控件放在一起读。去掉这句后，用户如果仍能从同一屏知道要做什么、操作有什么影响、当前是什么状态，就删掉。比如账号管理列表已有角色、状态和编辑入口时，标题下无需再介绍“为普通账号分配角色、启用或停用账号”。
- 自审时扫读标题区、列表或表单、空态、弹窗及操作反馈。文案应对应实际状态和后果。例如，停用会撤销会话的账号时，仍需提示会话失效。

## 设计依据

- 阅读适用的 `AGENTS.md`、PRD、架构、目标任务卡、现有页面代码和 UI 规范。确认用户入口、主操作、业务边界、数据变化和用户可见状态。沿用已有设计稿和已确认的产品风格。
- 根据请求选择首次设计、局部迭代或验收。新功能先按下文流程确认需求和原型，再按用户已授权的范围实现可运行页面。
- 排版前，从用户正在使用的页面走一遍最常见的任务，再决定用页面内入口、浮层、面板还是独立页面。扫读、确认或打开一条记录时，优先检验能否就地完成。频繁检索、比较、翻阅大量记录或连续操作时，根据实际内容量和工作深度评估独立页面。用代表性数据核对所选布局占用的空间和切换成本。

## 视觉方向与质量标杆

- 首次设计、视觉重做或用户明确要求提升质感时，先根据产品定位、使用场景、核心操作、信息密度和品牌气质确定构图、排版、素材与动效方向。展示页可以围绕主视觉组织叙事，高频工具页优先让入口容易找到、信息好扫读、操作反馈及时。已有明确风格的局部改动沿用项目规范。
- 以 Apple 的信息层级、控件一致性、交互反馈、适配与无障碍，以及米哈游的构图、素材和动效完成度作为质量标杆。按产品任务与气质建立自己的视觉语言。[Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/design-principles/)
- 首次设计、视觉重做或遇到现有规范难以覆盖的新页型时，由 Agent 主动使用可用的网页搜索、图片搜索和浏览器查找并筛选参考。按目标用户、任务类型、使用频率、信息密度和视口判断适配程度，优先查看实际产品页面、完整界面和相关交互。用户提供的参考纳入判断；来源受限时改查可访问的同类来源，并说明实际查看范围。
- 从少量有明确借鉴目的的参考中，提炼信息层级、布局比例、排版、用色、素材和交互做法，说明它们如何解决当前页面的问题。将适用做法统一到项目的视觉语言、设计变量和组件中，用真实业务内容试排。参考搜索、筛选和具体设计取舍由 Agent 完成，随原型简要说明依据。局部迭代优先复用已确认的规范，按实际缺口补充调研。
- 以一张最能体现体验的页面定方向，用接近真实的内容、数据和边界状态验证。方向明确时集中打磨一个方案，方向存在重要分歧时再给少量有实质差异的方案。用户可用“太挤”“重点不清楚”等感受反馈，Agent 将反馈转成具体设计调整并复查。

- 全局定方向时，从最常用或最重要的任务选择代表页，在项目资料记录用户、使用频率、信息密度及它们如何决定构图、排版、用色和素材。选用的参考链接、实际查看的页面或状态、借鉴点和适用范围随设计规则记入项目 UI 规范。若方案将用于不同任务类型，用接近真实的内容补测不同密度的页面。登录和设置等辅助入口的评审仅覆盖其自身场景。
- 记录视觉确认适用的页面、任务与视口。加入新页型、内容密度显著变化或用户否定整体观感时，重新检验受影响的共用规则。组织可复用的语义颜色和控件状态，按用途区分表面、文本、主操作、选中、业务状态与反馈。项目的题材、素材及数值留在项目 UI 规范。

## 预览与交付前自审

- 页面生成后、首轮交付前，单独做一轮视觉复审。以资深 UI/UX 设计总监的视角，从正常入口重新打开并操作代表性页面，按前文的 Apple 产品级精细度检查整体构图、排版、间距和对齐、视觉细节、装饰及交互反馈。以实际截图和操作判断问题及其影响。
- 第一次提交预览前，把首屏构图、素材与表单或列表的搭配、关键交互和动效放在同一版里验证。打开桌面和适用的窄视口，按真实入口完成主操作及相关异常状态。自行修正并复查后，提交可操作的高保真原型。实际实现交付前再次检查，局部改动按影响范围执行。
- 按页面风险选择组合场景，在实际页面中进入该状态并截图。有吸底栏或浮层时，组合窄视口、滚动和较长的失败提示，确认当前输入、提示和主要操作能同时看清，按钮仍可使用。在状态切换后的临时提示仍显示时截图，检查提示、结果内容和焦点是否互相遮挡。修复后在相同视口和状态复拍对照。
- 对下拉菜单、日期选择器等有独立展开面的控件，在目标浏览器从正常入口实际展开，检查闭合态与展开态的视觉一致性、选中态、键盘焦点及窄屏里的定位和遮挡。自动化直接设值可验证表单逻辑，展开态验收需看到实际呈现。需要定制时优先复用可定制的原生控件或现有组件，并验证适用的键盘、触控和回退行为。
- 从首屏和任务路径判断视觉主次。列表列宽以快速扫读为准，长表单按填写节奏组织，长段正文按可读行宽收束，关联页面沿共用边线对齐。需对比的信息可在宽屏并排，在窄屏按阅读和输入顺序堆叠。用接近真实的密度和长标题、长名称等边界内容验证，确保用户能查看完整值。
- 有列表到详情的路径时，在同一桌面视口分别截图，对照两页在主工作区里的左右边线和边距。分别核对页面外框的宽度和长段正文的行宽，并按各自用途确定宽度。
- 检查复用组件在页面上的接合处。核对相邻组件是否叠出双边线或重复留白，新增控件是否沿用同列宽度和基线，摘要换行后是否把主要内容或操作推得过远。
- 排查通用模板感。检查重复头像、描边、卡片、渐变、徽章、箭头和说明是否各有用途。尤其核对控件外观与动作是否一致，例如打开编辑弹窗的按钮无需加表示跳转的箭头。保留能帮助辨认、判断和操作的线索。在接近实际密度的整屏样本中，对照同类和混合数据的扫读效果。上下文已说明的重复信号可以降低强调，保留必要的文字与识别线索。
- 把反馈放在可以采取行动的位置。字段报错贴近对应控件并给出修正方法，提交校验失败后聚焦首个待修正字段。写入失败在重试操作附近提示，保留输入、滚动位置和主按钮位置。窄屏有吸底操作栏或面板时，在适用的触屏环境验证软键盘、滚动和较长提示同时出现时的可读性与可操作性。
- 用键盘走一遍关键路径，检查焦点位置、焦点指示和实际可见性。聚焦元素应完整可见且可操作，必要时滚动页面，使焦点避开遮挡。验证失败重试、提交成功、关闭面板和返回列表时，焦点落在用户下一步需要阅读或操作的位置。写入后返回列表时，用代表性数据核对用户能否定位到刚变更的记录，并检查滚动和焦点是否支持下一步操作。验证同名或排序变化等适用情况。
- 在已确认的业务范围与视觉方向内，自己筛选素材、试排版、调动效，把发现的问题合并修完再交付预览。把评审意见集中到整页与主要流程。仅当需要决定未确认的业务规则、关键交互或整体视觉方向时，才征求意见。交付时给出预览入口、值得试的操作和实际验收结果。
- 复审发现具体问题时，在当前范围直接修复，交付时说明实际修复、首轮漏验的条件和复测结果。把可复用的验收改进写入此 Skill，并按已有授权同步本机与归档。复审通过时沿用当前方案，报告实际检查范围和结果。
- 对从现有页面发起的短任务，从原任务中实际打开入口、完成操作并返回。检查是否需要切页、能否保留输入与位置、关闭后焦点回到哪里，以及常见内容量在桌面和窄屏是否适合所选布局。

- 复审分别记录产品适配、视觉精细度、交互可用性的结论及实际证据。方向重做时，用相同的代表性内容和数据，将改动前后的核心页面在相同视口对照，核对首屏重点、信息节奏、素材完成度与相邻页面是否协调。参考研究后的效果以实际页面和任务体验验证，结论对应具体可见变化。能走通流程和没有溢出是交互与布局证据。若构图、排版或控件质感仍停留在草案阶段，先继续打磨再作为高保真稿交付。

## 主视觉与图片

- 需要主视觉时，先从产品的使用场景和气质选一个看得懂的主体或动作，再定表现手法、色调、材质和裁切。可用排版和留白建立焦点的页面也可直接采用纯内容构图。
- 在实际页面里选图。先看主体与任务的关联、素材工艺和辨识度，再看图片与标题、主按钮的相对大小、视线顺序、对齐、间距和底色。画面本身成立但在布局里显得突兀时，先试缩放、裁切、移位或调整周边留白。主体与产品气质有偏差时重新选图。
- 在桌面和窄屏检查裁切、主体完整度、叠字对比度及首屏空间。空间受限时，按任务决定缩小、重排或省略配图，让主操作保持可见。首次评审在实际渲染的原型里呈现选定的配图和构图。

## 交互动效

- 为能帮助用户理解状态变化、定位变化或承接操作的动效明确触发点、变化区域、稳定参照和结束状态。沿用项目已有的节奏，按变化范围和操作频率调整时长。高频操作中保持控件可操作，结束后将焦点放到符合操作顺序的位置。
- 局部变化时保留导航、标题、公共字段等稳定参照，留意滚动条、提示或按钮文案变化引起的错位。例如切换事项类型只让专属字段区过渡，保存后在列表短暂标记更新的行。列表和详情往返时按需要恢复原记录的焦点与滚动位置。涉及同一区域的内容替换时，检查旧内容退出与新内容进入的顺序，避免文字重叠。
- 在浏览器里实际触发并观察开始、中间和结束。必要时逐帧看重影、闪白、裁切或布局跳动。验证快速切换、提交中、失败后重试等适用状态，也验证减少动态效果时仍有完整反馈且可以完成操作。涉及忙碌文案时，在同一视口对照操作前、请求中和结果出现时，检查按钮及相邻操作的位置、可见焦点与可用性。

## 字体与排版

- 按项目气质、阅读场景和信息密度选字体，优先沿用合适的项目字体。新选字体时，用页面实际的中文、拉丁文字和数字试排，确认字形搭配、字重和回退字体合适。
- 分别设计标题、正文、辅助文字和数字的层级。用字号、字重、行高和字距调整阅读节奏，保持标题与正文易于区分，标签和提示易于扫读。金额、日期等需要纵向比较的数字可用等宽数字，并检查单位、小数位和列对齐。
- 涉及排版的任务，在桌面和适用的窄视口检查实际渲染。用长标题、多行正文、真实范围内的大数值和状态提示核对字距、换行、截断、溢出和数字对齐。使用自定义字体时，确认页面实际加载了所选字体，并检查回退时的可读性与布局。

## 按功能逐步设计

项目整体规划时先理解产品定位、目标用户与整体信息架构，再确定视觉方向。首次 UI 设计阶段与用户确认项目名称，设计确认后提供英文项目名供用户创建项目，再按用户提供的项目路径交接。后续功能沿用已确认的风格与组件。用户选定下一项新功能后，先确认当前功能的具体业务规则、交互和可观察的验收条件，再设计对应页面与状态。

将可查看的高保真原型和预览入口交给用户，关键交互应可操作。原型可用独立页面及模拟数据。用户明确确认当前原型后，将相关规则更新到 UI 规范。进入产品实现前，先完成下文「实现与验收」的开工说明。等待评审时保持当前阶段为原型设计。

## 首次设计与交接

1. 用选定的视觉方向规划页面结构、主次操作和关键视口，确认核心操作在合理的浏览范围内可以直接完成。
2. 制作高保真原型，覆盖当前功能所有已确认的页面、角色入口、操作路径及适用的可见状态。先据 PRD、任务卡和实际代码列出覆盖清单，逐项映射到可查看的画面或可操作状态：包括初始、输入与校验、提交中、成功、空、失败、权限受限、恢复及关键边界等适用情况；不适用项说明原因。相同表现可复用组件，但不同结果与必要反馈须可分别查看。未确认业务规则先澄清或标记未决，不虚构；明确报告未覆盖和未验证项，不能将部分原型称为完整覆盖。将影响体验的交互与动效做进预览，并提供可直接走到这些状态的入口或简短操作说明。
3. 完成预览前自审后提交原型评审。视觉方案确认后，向开发交接原型位置、任务及需求 ID、关键视口、布局、排版规则、颜色、间距、组件和状态行为。关键动效注明触发、顺序和结束状态。将可复用规则记入已有 UI 规范，默认路径为 `docs/UI_DESIGN.md`。用于试跑的未确认规则标为草案，说明所采用的设计假设。

## 局部迭代

检查现有规范和受影响页面。优先延续现有信息架构、组件和操作习惯，仅调整与本轮需求相关的区域。发现确需变更的通用规则时，说明影响并同步 UI 规范。

## 实现与验收

1. 核对本功能的需求和适用原型已由用户确认。按本轮实际准备实现的页面、交互、接口和数据确定说明详略。进入功能实现时，先在对话中讲清业务逻辑、重要数据、设计理由、带关键分支的链路图及真实入口的验证方式，再使用现有技术栈和设计变量修改产品代码。若实际只改文案或样式，说明位置和验证方式即可。从已确认原型进入完整实现时，按实际功能范围说明。
2. 在环境支持时启动实际页面，在目标桌面与适用的窄视口查看并截图。对照已确认的原型和 UI 规范完成交付前自审，检查素材裁切及实际组件状态。
3. 通过真实入口操作主流程和相关失败路径，验证表单提示、状态切换及必要的键盘操作。按交互动效要求检查实现中的关键过渡。对照任务卡核验结果，修正明显差异后复查。
4. 从原型转入完整功能实现或局部交互改变业务行为时，按 `plan-vertical-slices` 的「开发执行模式」核对开工说明与最终答复，最终正文要交代实际逻辑与关键失败反馈。汇报实际检查的页面、视口、交互和证据。涉及文案改动时，记录删除的重复信息和确认可见的必要提示。无法实际渲染或执行的检查标记为「待验收」。按实际证据更新任务状态。
