# 共创与维护 PRD

以产品经理视角维护一份能指导当前开发的主 PRD。以用户确认的范围为准，按功能复杂度决定详略。发现影响产品目标、业务一致性或可用性的设计问题时，简述影响并给出推荐。重大产品决策由用户确认。

## 确定当前范围

- 确定目标项目，阅读适用的 `AGENTS.md`，定位并读取最新主 PRD。沿用已有路径和格式。新项目默认使用 `docs/PRD.md`。在维护时以实际保存的版本为准。
- 区分已确认需求、待确认决策、未来想法和 AI 建议。只有已确认需求进入正式功能总览和开发范围。非阻断细节可采用可逆默认值，必要时标为暂定。遇到影响当前方向、核心业务规则或可交付性的关键决策时，给出推荐并询问，原则上每轮最多两个问题。
- 用户明确要求查看完整 PRD 时，返回实际保存的最新版本。纯技术重构、内部优化和恢复已确认行为的修复通常无需修改 PRD。发现实现与 PRD 不一致时，先判断是实现偏差还是已确认的需求变更，以此决定修复代码或同步文档。

## 首次创建

1. 梳理产品定位、目标用户、核心场景和首批功能。方向、场景和首批范围足以指导开发时，直接交付当前版本。未确认的未来能力留在想法池。
2. 写出一份完整而简洁的 PRD，默认包含以下部分。
   - **产品概述** — 产品定位、目标用户、核心问题与体验、当前版本目标。
   - **功能总览** — 用表格记录稳定的功能 ID、名称、所属模块、优先级和功能级开发状态。新功能默认「待开发」。按需使用 P0、P1、P2。
   - **功能详细说明** — 用 `F001｜功能名称` 关联总览。写明功能目标、用户操作与系统反馈、关键业务规则、可观察的验收标准。按复杂度补充交互、状态、异常及依赖。
   - **想法池与待定事项** — 记录未来想法、待决事项及必要的范围边界。尚未确认的内容不分配正式功能 ID。
3. 在目标项目中保存，核对保存后的内容。首次向用户交付完整 PRD。没有写入条件时，直接提供完整的可保存 Markdown，并说明保存状态。

## 增量维护

1. 先读原文并定位功能 ID。新增时检查是否重复或冲突。修改或删除时核对关联需求、依赖和验收标准。
2. 已确认的增删、交互、业务规则和范围变更，在本轮主动更新主 PRD。修改受影响的条目、总览和必要关联内容，保留无关条目及已有功能 ID。讨论中的想法留在想法池或对话中。沿用项目的版本管理约定。
3. 若同轮包含开发，先同步已确认的行为变更，再按授权范围实现和验证。PRD 的「待开发」「开发中」「已完成」描述功能整体，切片进度由项目任务系统维护。功能的必要验收均有通过依据时才标记「已完成」。
4. 检查并报告本轮功能 ID、关联变化、重要待定事项和保存结果。没有写入条件时，提供可合并的增量内容。日常迭代反馈变更即可，完整 PRD 按需展示。

## 质量检查与交接

- 核对总览和详情的 ID 一致，确认正式范围来自用户已确认的需求，规则和依赖无明显冲突。验收标准写清触发条件、用户操作和可观察结果，覆盖主流程及影响交付的异常。
- 向任务规划交接时，给出主 PRD 路径、已确认的功能 ID、验收标准所在位置及影响拆分的待定事项。`$plan-vertical-slices` 可使用该 PRD 和项目架构、代码进行拆分。仅在用户要求规划或开发时进入相应阶段。

## 项目规划与按需细化

用户希望规划完整新项目时，先确认产品目标、角色、功能范围与建议顺序，形成概览级 PRD；不逐一追问后续功能的字段和细节。随后衔接技术选型与架构、功能卡片；选定当前功能后先确认该功能必要细节并更新 PRD 和任务卡；在设计 UI 时与用户确定项目名称，再设计对应 UI。用户确认设计后，明确提供英文项目名供用户创建项目；用户创建后取得项目路径，其他页面随功能逐步设计，按用户决定逐步推进；完成当前阶段所需的确认后主动进入下一阶段。项目尚未创建时将成果保存在当前可写位置，标明建议迁移路径；用户提供项目地址后，核对已有文件及适用指令，合并已确认成果到项目对应路径，避免覆盖现有内容，并主动处理项目根目录 AGENTS.md：存在时读取并保留，必要时仅合并适用的已确认约定；不存在时使用用户的工作流模板（如有）结合项目实际情况创建，涵盖 Skill 使用、文档路径、任务和验收约定，并写明开发或修复完成并检查后自动暂存本轮适合版本控制的改动；保留既有暂存和未暂存改动，混合改动无法安全区分时不暂存并说明，提交和推送仍按用户授权。新建或增量维护项目 AGENTS.md 时，写入 Git 提交文案规范。默认标题采用 `类型(范围): 中文摘要`，范围可省略，英文半角冒号后加空格。简单改动用一行。复杂改动在标题后空一行，用 `- 【新增】 …`、`- 【修改】 …`、`- 【修复】 …` 逐条说明功能或模块的具体变更和影响。将表、字段和约束的变化写入对应功能。原型或测试代码本身是交付内容时，说明交互或覆盖的行为。部署、建库、迁移、备份和恢复步骤写入运行或维护文档。测试次数、构建结果和浏览器验收写入验收记录或交付汇报。需求确认和任务卡同步过程留在项目文档。交付阶段的提交文案检查可沿用 plan-vertical-slices。同时写入 README 规则：按企业级文档标准面向使用、部署和维护，语言简洁、避免演示口吻及冗余解释；即使开发中也以成熟项目方式组织内容，功能、命令与状态必须真实，未完成或未验证内容如实标注。未知命令不编造。回读并检查交接文档及相互引用，提供新对话可用的交接摘要。不假设已创建项目或已迁移。

用户选定下一项新功能时，先核对当前任务的需求、代码和依赖。整理影响实现和验收的业务行为、权限、重要异常及可观察的验收条件，向用户确认尚未明确的关键规则。可按影响分组提问并给出建议，已确认内容直接沿用，常规细节可标为可逆默认值。用户只回答部分问题时，更新对应条目并继续确认其余会改变行为或验收的决定。

用户确认本功能的业务规则和验收条件后，更新 PRD、任务卡及受影响的架构约定，再把涉及界面的功能交给 design-product-ui 制作原型。按 plan-vertical-slices 的阶段约定进入实现，保留用户对需求和适用原型的确认依据。
